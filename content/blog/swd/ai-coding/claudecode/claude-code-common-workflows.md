> 好的 Claude Code 提示词不是“写得很长”，而是让目标、边界和验收结果都能被检查。

## 先建立一个共同的工作习惯

Claude Code 适合处理完整的研发任务：它能搜索代码、读取上下文、修改文件、执行命令，再根据结果继续判断。真正容易失控的情况，是用户只说“把这个做好”，却没有说明改动范围和完成条件。

一个足够实用的任务描述通常包含四件事：

- **目标**：希望最终得到什么结果；
- **范围**：允许查看和修改哪些文件或模块；
- **约束**：必须遵守的接口、兼容性或风格；
- **验证**：完成后必须运行哪些检查，什么结果算通过。

例如，与其说“优化登录”，不如说：

```text
检查 src/auth/ 下的登录流程，定位重复查询造成的延迟。
只修改认证模块和对应测试，不改公共 API。
完成后运行认证测试，并说明是否还需要手工验证。
```

## 探索陌生代码库时，先问地图再问细节

第一次进入项目，不需要让 Claude 读完整个仓库。让它先看项目入口、依赖清单、构建脚本和少量关键目录，再逐步缩小范围：

```text
请了解这个项目的技术栈、启动命令、测试命令和主要目录。
只阅读能回答这些问题的文件，不要修改任何内容。
```

有了地图后，再沿着一个真实请求追踪：

```text
从登录表单开始，追踪一次登录请求经过的前端、API、服务和持久化层。
请列出实际读取过的文件，并指出你还没有验证的假设。
```

已知路径时，使用 `@` 可以减少搜索范围：

```text
解释 @src/auth/session.ts，并对照 @src/api/login.ts 说明会话是在哪里创建的。
```

大型仓库中，探索结果可能远多于主任务需要的内容。可以让 Claude 使用 Explore Subagent，或者直接说“把探索结果压缩成结论、文件路径和待确认问题”，把主会话留给实施。

## 修 Bug 要把“现象”变成“可重复证据”

错误消息只是线索，重现命令和输入才是证据。一个有效的修复请求应当包含：

```text
运行 `npm test -- auth` 可以重现失败。
请先确认失败稳定出现，再追踪调用链，解释根因。
不要通过删除断言、放宽类型或吞掉异常来消除错误。
修复后运行原测试，并补一个能覆盖根因的回归测试。
```

如果问题来自浏览器，可以附上截图或让 Claude 通过 Chrome 读取控制台和 DOM；如果问题来自 CI，则给出失败的 job、日志文件和触发提交。让 Claude 先复现再改代码，通常比直接粘贴一段错误信息更省返工。

修复完成后，检查三件事：

1. 修改是否落在预期文件；
2. 回归测试是否真的覆盖了原始失败；
3. 是否有新的警告、类型错误或未运行的检查。

## 大范围改动先用 Plan Mode

跨模块重构、公共 API 变化和数据迁移不适合直接进入编辑模式。可以在会话中切换到 Plan Mode，也可以从命令行启动：

```bash
claude --permission-mode plan
```

规划阶段的提问要限定研究范围：

```text
检查 src/utils/ 中仍在使用旧 API 的函数。
请给出受影响文件、调用方、迁移顺序和回滚风险，不要修改文件。
```

计划需要能被审查，而不是只有“重构、测试、提交”三个抽象词。至少应说明：哪些文件会变、哪些接口不能变、每一步如何验证、遇到失败如何停下。

批准计划后再切换到 `acceptEdits` 或手动模式实施。让 Claude 分批修改并在每个稳定边界运行检查，能把错误留在离根因最近的地方。计划不是替代测试，计划只是在动手前减少方向性返工。

## 测试要覆盖行为，不要只追求绿色

让 Claude 补测试时，先说清楚行为和边界：

```text
为 parseConfig 增加测试：
- 合法配置返回默认值与用户值的合并结果；
- 缺少必填字段时返回可识别的错误；
- 未知字段不会改变核心结果；
- 输入为空时不会抛出未处理异常。
先阅读现有测试风格，再写测试并运行相关文件。
```

测试失败时，不要让 Claude 直接改测试直到通过。可以要求它先判断失败属于实现错误、测试预期错误还是环境问题，再决定修改哪一侧。涉及安全、权限和输入校验的测试，尤其不能为了绿灯而删除断言或降低校验强度。

常见的验证组合是：局部测试、类型检查、Lint、构建和必要的手工检查。项目已有命令应优先写进 `CLAUDE.md`，避免 Claude 每次猜测包管理器和参数。

## Git 操作要保持可审查

Claude Code 可以读取状态、查看 diff、生成提交信息和创建 Pull Request，但 Git 的不可逆动作仍应保留人工边界：

```text
查看当前工作树和 staged diff。
把与本任务无关的修改列出来，不要覆盖它们。
确认测试结果后，给出一条 commit message，但先不要提交。
```

要从现有 Pull Request 继续工作，可以使用：

```bash
claude --from-pr 123
```

要让多个任务互不覆盖，可以使用 Git worktree：

```bash
claude --worktree auth-refactor
```

Worktree 适合相互独立的任务；同一文件、同一数据库或高度依赖的改动，仍应由一个会话顺序完成。并行不是越多越好，整合成本通常会随着并发数上升。

## 代码审查要让审查者独立于作者

当前工作区审查可以直接使用捆绑 Skill：

```text
/code-review
```

也可以给出审查维度：

```text
审查当前 diff，优先检查：
- 认证和授权边界；
- 并发与重试逻辑；
- 错误处理和日志中的敏感信息；
- 测试是否覆盖新增分支。
只报告能够定位到文件和行的具体问题，并说明为什么会造成风险。
```

审查输出最好经过第二个 Subagent 或人工复核，不要把“模型提出了问题”当作问题已经成立。对重要 Pull Request，可以让一个代理找问题，再让另一个代理尝试反驳或复现，最后由主会话汇总。

## 小任务可以直接调用，长任务要隔离

Claude Code 里有几种很实用的短路径：

```text
/debug             进入调试流程
/batch             批量处理相似文件
/simplify          检查刚改过的代码是否能更简单
/run               启动项目并观察实际行为
/verify            构建并运行项目，确认改动在运行时成立
```

这些命令中有些是捆绑 Skill，不是硬编码的内置命令。它们会消耗模型上下文，因此应当在任务确实需要时使用。

如果探索、日志或文档查找会产生大量中间输出，可以明确要求：

```text
请用一个只读 Subagent 检查所有 API 路由的鉴权情况。
返回文件路径、风险等级和证据，不要修改任何文件。
```

当任务规模超过几个独立 Subagent，或者需要对结果交叉核验，可以请求动态工作流；例如 `/deep-research` 会并行查找、验证并汇总来源。它解决的是编排和核验，不是让每个小任务都多开一层代理。

## 终端本身也可以成为工作流的一部分

在输入框中以 `!` 开头，可以直接运行 Shell：

```text
! git status --short
! npm test
```

长时间运行的开发服务器或测试可以按 `Ctrl+B` 放到后台，再让 Claude 继续处理前台任务。后台任务可以在 `/tasks` 中查看；退出会话时，普通后台命令会按 Claude Code 的生命周期规则清理。

脚本化场景使用 `claude -p`：

```bash
git diff main...HEAD | claude -p \
  "只审查这个 diff 的安全问题，输出文件、行号、问题和建议" \
  --output-format json \
  --bare \
  --allowedTools "Read"
```

`--bare` 适合 CI 和可重复脚本，它不会自动加载本机的 Hooks、Plugins、MCP、Auto Memory 和 `CLAUDE.md`。如果脚本需要这些内容，应当用 `--settings`、`--mcp-config` 或显式提示传入，而不是默认依赖运行机器。

## 定时任务和会话恢复

需要在同一个会话里轮询状态、重复运行提示词或设置一次性提醒时，可以使用 `/loop`。需要更完整的云端自动化，则应区分 Desktop Scheduled Tasks、Cloud Routines 和本地 CLI 定时任务，先确认任务运行在哪里、凭证由谁持有。

会话恢复常用三种方式：

```bash
claude --continue
claude --resume
claude --resume release-prep
```

如果只是切换到不相关的任务，优先使用 `/clear` 重新开始；如果仍需要原来的结论，则先给会话命名，再从 `/resume` 找回。`/compact` 适合保留当前任务脉络，不适合把完全无关的历史强行压缩到一起。

## 把工作流写进项目，而不是写进记忆

当一套任务连续出现时，先把它写成可检查的 Skill 或项目规则：输入是什么、允许改哪些文件、验证命令是什么、失败时如何停下。只有长期稳定的项目约定才放进 `CLAUDE.md`，偶尔使用的长流程放进 Skill，固定且必须执行的动作放进 Hook。

这样做的好处不是“让 Claude 自动完成一切”，而是让每次执行都能追溯到同一份约束。你仍然要看 diff、看测试结果，并为推送、部署、发消息或修改生产数据保留确认边界。
